# Architecture Decision Records (ADR)

## Что такое ADR?

Architecture Decision Records (ADR) — это документы, которые фиксируют важные архитектурные решения, принятые в процессе разработки проекта. Каждый ADR описывает контекст, решение и последствия конкретного архитектурного выбора.

## Зачем нужны ADR?

1. **Историческая справка** - понимание, почему было принято то или иное решение
2. **Онбординг** - новые разработчики быстрее понимают архитектуру
3. **Избежание повторных дискуссий** - решение уже задокументировано
4. **Эволюция архитектуры** - видно, как менялись решения со временем
5. **Обучение** - команда учится на прошлых решениях

## Формат ADR

Каждый ADR следует структуре:

```markdown
# ADR-XXXX: Название решения

## Статус
[Предложено | Принято | Отклонено | Устарело | Заменено ADR-YYYY]

## Контекст
Описание проблемы и ситуации, требующей решения.

## Решение
Описание принятого решения.

## Последствия
Положительные и отрицательные последствия решения.

## Альтернативы
Рассмотренные, но отклоненные варианты.
```

## Процесс создания ADR

1. **Определите проблему** - четко сформулируйте, что требует решения
2. **Исследуйте альтернативы** - рассмотрите минимум 2-3 варианта
3. **Создайте ADR** - используйте шаблон выше
4. **Обсудите с командой** - получите feedback
5. **Примите решение** - обновите статус на "Принято"
6. **Реализуйте** - внедрите решение в код
7. **Обновите при необходимости** - если решение устарело, создайте новый ADR

## Нумерация

ADR нумеруются последовательно: ADR-0001, ADR-0002, и т.д.
Номер никогда не переиспользуется, даже если ADR отклонен или устарел.

## Статусы

- **Предложено** - решение предложено, но еще не принято
- **Принято** - решение принято и реализуется/реализовано
- **Отклонено** - решение рассмотрено, но отклонено
- **Устарело** - решение больше не актуально
- **Заменено ADR-XXXX** - решение заменено новым ADR

## Когда создавать ADR?

Создавайте ADR для решений, которые:

- ✅ Влияют на архитектуру системы
- ✅ Сложно изменить в будущем
- ✅ Имеют значительные последствия
- ✅ Вызывают дискуссии в команде
- ✅ Требуют обоснования выбора

Не создавайте ADR для:

- ❌ Тривиальных решений
- ❌ Временных workaround'ов
- ❌ Решений, легко обратимых
- ❌ Стилистических предпочтений (используйте style guide)

## Примеры хороших ADR

### Хороший пример

```markdown
# ADR-0001: Clean Architecture с Ports & Adapters

## Статус
Принято

## Контекст
Нам нужна архитектура, которая:
- Изолирует бизнес-логику от внешних зависимостей
- Упрощает тестирование
- Позволяет легко менять БД, фреймворки, UI

## Решение
Используем Clean Architecture с паттерном Ports & Adapters:
- domain/ - бизнес-логика, независимая от фреймворков
- usecase/ - use cases + интерфейсы (ports)
- adapter/ - реализации интерфейсов (HTTP, DB, etc.)
- infra/ - инфраструктурный код

## Последствия

Положительные:
+ Бизнес-логика изолирована и легко тестируется
+ Можно менять БД без изменения use cases
+ Четкое разделение ответственности

Отрицательные:
- Больше boilerplate кода
- Требует дисциплины от команды
- Сложнее для новичков

## Альтернативы

1. MVC - отклонено, т.к. смешивает concerns
2. Hexagonal Architecture - похоже, но менее структурировано
3. Layered Architecture - отклонено, зависимости идут вниз
```

### Плохой пример

```markdown
# ADR-0042: Используем Go

## Решение
Будем писать на Go.

## Почему
Потому что Go быстрый и простой.
```

Проблемы:
- Нет контекста
- Нет альтернатив
- Нет последствий
- Слишком общее

## Обслуживание ADR

### Регулярный review

- Раз в квартал просматривайте ADR
- Обновляйте статусы устаревших решений
- Создавайте новые ADR для замены устаревших

### Связывание ADR

Если новый ADR заменяет старый:

```markdown
# ADR-0020: Новое решение

## Статус
Принято (заменяет ADR-0005)

## Контекст
ADR-0005 больше не подходит, потому что...
```

И обновите старый ADR:

```markdown
# ADR-0005: Старое решение

## Статус
Заменено ADR-0020

## Причина замены
[Объяснение]
```

## Best Practices

1. **Пишите ADR до реализации** - не после
2. **Будьте конкретны** - избегайте общих фраз
3. **Документируйте альтернативы** - покажите, что рассмотрели варианты
4. **Указывайте последствия** - и положительные, и отрицательные
5. **Используйте простой язык** - ADR должен быть понятен всем
6. **Добавляйте ссылки** - на обсуждения, документацию, код
7. **Обновляйте статусы** - держите ADR актуальными
8. **Не удаляйте ADR** - даже отклоненные полезны для истории
